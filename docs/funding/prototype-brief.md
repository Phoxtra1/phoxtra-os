# Phoxtra OS — Prototype and R&D Funding Brief

**Stage:** Early-stage bootable operating-system prototype  
**Current validated environment:** x86_64 QEMU virtual machine in automated CI  
**Physical laptop validation:** Pending  
**Mobile-phone version:** Not implemented  
**Dedicated Phoxtra hardware:** Target not selected; software readiness preparation only

## Executive summary

Phoxtra OS is an operating-system research and development project intended to form part of the software foundation for future Phoxtra devices. The current x86_64 prototype boots from a GRUB/Multiboot2 ISO and includes a graphical desktop environment, keyboard and pointer paths used in automated virtual-machine testing, a small set of built-in system panels, an application catalogue, and a read-only hardware readiness report.

A GitHub Actions pipeline builds the kernel and ISO, builds additional product profiles, checks storage-safety invariants, boots the ISO in QEMU, and exercises selected desktop interactions. Successful workflow runs provide evidence of reproducible compilation and the specific automated behaviors tested. They are not proof of universal hardware compatibility or production readiness.

The project is seeking an appropriate route to support further prototype engineering, testing, hardware validation, and preparation for future device integration. The requested support should be matched to a funder's rules; eligibility and funding are not assumed.

## Problem and opportunity

An integrated OS/software platform can be part of a longer-term hardware product strategy, allowing a device maker to coordinate system software, device behavior, and product-specific applications. Phoxtra's current work is an early technical exploration of that direction, not yet a commercially ready platform.

## Current evidence

- A bootable x86_64 ISO is generated by the build pipeline.
- Automated CI checks kernel compilation and desktop/embedded profile builds.
- QEMU checks exercise framebuffer startup, shell/desktop event-loop startup, theme switching, catalogue access, file-manager mouse interaction, RAM-backed file/folder creation, and screenshot sanity.
- CI attaches a disposable SATA disk through QEMU AHCI, verifies read-only sector I/O, mounts an ext2 partition read-only, reads a file through the VFS, and checks that the base disk-image SHA-256 is unchanged.
- A read-only hardware report inventories selected PCI classes and distinguishes a simulated RAM disk from registered physical block-device support.
- MBR partition discovery, supported physical disk reads, and the ext2 path are read-only; the installer, formatting, and disk writes remain disabled.

Evidence should be attached to any proposal as dated CI run links, commit IDs, test logs/screenshots, and the current limitations statement. Only include a CI run if it is still accessible and relates to the code being described.

## Current limitations and risks

- No physical-laptop acceptance test has yet been recorded.
- An experimental read-only AHCI/SATA driver and limited on-disk ext2 reader are exercised in QEMU CI. Support is limited to ATA LBA48 disks with 512-byte logical sectors; this is not yet validated on a physical laptop.
- Writable persistent storage, NVMe, on-disk FAT32, ext2 journal/index support, installation, formatting, and write-based recovery are not implemented. The 32 MiB RAM test disk is volatile; RAM-backed demo files are lost on reboot.
- The installer is disabled.
- The Amineva Global product entries and Amineva Workspace are catalogue entries, not functioning integrated external apps.
- The prototype does not deliver a complete browser/HTTPS user feature.
- The kernel, driver coverage, security model, recovery/update path, and long-term stability need additional engineering and review.
- No dedicated hardware board has been selected or validated.
- There is no implemented and validated mobile-phone build.

These limitations should be included in funder conversations. The prototype must not be described as a finished operating system.

## Proposed use of support

Prioritize work in measurable stages:

1. **Prototype hardening:** kernel/runtime audit, fault handling, memory and interrupt correctness, automated regression coverage, build reproducibility, and accurate diagnostics.
2. **Persistent storage engineering:** broaden read-only driver and filesystem compatibility, then separately design and review safe writes, flush semantics, corruption handling, installation, backup, and recovery; keep all physical writes disabled until their tests and safety review pass.
3. **Network and application runtime:** validate supported network hardware, DNS/TCP/TLS/certificate handling, then select and integrate an appropriate browser/runtime or native application contract.
4. **Amineva Workspace integration:** use verified service endpoints, tested authentication and session lifecycle, file flows, and explicit offline behavior.
5. **Physical validation:** test on a standard laptop, record device-specific results, fix and retest release blockers.
6. **Hardware feasibility:** after laptop acceptance, select a real target board and prepare a costed bring-up plan including firmware, display/input, storage, power, thermals, and recovery.
7. **Distribution readiness:** versioned draft releases, checksum verification, documentation, reproducible artifacts, and backup/download hosting.
8. **Mobile feasibility study:** treat ARM64 phone support as a separate architecture and hardware programme, not an automatic extension of the current x86_64 ISO.

## Deliverables and measurable milestones

- CI run logs and reproducible ISO/checksum for each reviewed commit.
- An updated issue/milestone register showing pass/fail/blocked status.
- A completed standard-laptop validation report when physical testing occurs.
- A reviewed storage architecture and tests before any physical-disk writes are enabled.
- A verified Workspace integration matrix before the suite is labelled integrated.
- A target-board specification and costed hardware bring-up plan before hardware claims are made.
- A draft release and versioned technical documentation before public distribution.

## Suggested funding routes to investigate

Depending on eligibility and geography, look for:
- Early-stage hardware/embedded systems or operating-system R&D support.
- Prototype and proof-of-concept grants.
- University engineering labs, research partnerships, and maker/incubator programmes.
- Technology accelerators that accept pre-revenue technical prototypes.
- Strategic partnerships with device manufacturers, embedded systems engineers, and test laboratories.

Before applying, confirm whether the programme accepts individual founders or companies at this stage, requires incorporation or local presence, funds software-only work versus hardware purchases, requires matching funds/equity, and expects a working physical prototype. Do not pay application, investment, or visa-related fees based solely on an unverified promise of funding.
